# 동료평가 설명서 — B4-1 컴퓨터가 알아서 자기 상태를 점검하게 만들기

> **평가 중에 이 문서를 열어놓고 그대로 읽으셔도 됩니다.**
> 평가표 문항 **순서 그대로** 정리했고, 문항마다
> ① 평가자가 확인하는 것 ② 실행할 명령 ③ 나올 결과 ④ **읽을 말**을 묶어두었습니다.
>
> 읽을 말은 `>` 로 시작하는 인용 블록입니다. 외우지 마시고 읽으세요.
> 다 읽을 시간이 없으면 **굵게** 표시된 문장만 읽어도 핵심은 전달됩니다.

## 시작하기 전에 — 한 줄로 환경 켜기

```bash
./run.sh up          # 컨테이너 + 설정 전체 (처음 또는 재구성할 때)
./run.sh app         # 앱 실행 → Boot Sequence 5단계가 보인다
./run.sh evidence    # 평가표 8개 증거가 순서대로 전부 출력된다
```

**컨테이너를 재시작했다면 방화벽을 반드시 다시 올리세요.**

```bash
docker exec agent-ops ufw --force enable
docker exec agent-ops ufw status verbose     # Status: active 확인
```

> 왜 매번 다시 올려야 하는지는 **항목 1-②**의 읽을 말에 들어 있습니다.
> 평가자가 물어볼 수 있는 좋은 포인트입니다.

## 1-① SSH 포트 20022 + Root 원격 접속 차단

**명령**
```bash
grep -E "^(Port|PermitRootLogin)" /etc/ssh/sshd_config
```
**나올 결과**
```
Port 20022
PermitRootLogin no
```

**읽을 말**

> "SSH 설정 파일에서 두 줄을 바꿨습니다. 포트를 22에서 **20022로 옮기고**,
> **root 원격 로그인을 막았습니다.**
>
> 포트를 바꾼 이유는, 22번이 전 세계가 아는 기본 포트라서 서버를 인터넷에 올리면
> **몇 분 안에 자동 스캐너가 두드리기 시작**하기 때문입니다. 포트를 옮기면
> 그 자동화된 소음이 거의 사라집니다.
>
> 다만 **이건 막은 게 아니라 비용을 올린 겁니다.** `nmap` 한 번이면 찾아냅니다.
> 그래서 키 인증과 방화벽과 **함께** 써야 의미가 있습니다.
>
> root 차단이 더 본질적입니다. 공격은 '계정 알아내기 + 비밀번호 뚫기' 두 단계인데,
> **root는 1단계가 공짜**입니다. 모든 유닉스에 반드시 있는 이름이니까요.
> 막아두면 ① 계정 이름까지 맞혀야 하고 ② 뚫려도 일반 권한이라 권한 상승이 더 필요하고
> ③ `sudo`를 쓰게 되니 **누가 무슨 명령을 했는지 로그에 남습니다.**"

**구현 위치** — `setup/03_ssh.sh`. 기존 줄이 있으면 바꾸고 없으면 덧붙이는 `set_option()` 함수로 처리했습니다. 주석 처리된 줄(`#Port 22`)도 함께 잡도록 정규식에 `[#[:space:]]*`를 넣었습니다.

## 1-② 방화벽 활성 + 20022·15034 **만** 허용

**명령**
```bash
ufw status verbose
```
**나올 결과**
```
Status: active
Default: deny (incoming), allow (outgoing), deny (routed)

20022/tcp   ALLOW IN   Anywhere   # SSH (changed from 22)
15034/tcp   ALLOW IN   Anywhere   # Agent App
```

**읽을 말**

> "**기본 정책을 '들어오는 건 전부 차단'으로 두고, 필요한 두 포트만 열었습니다.**
>
> 순서가 중요합니다. '일단 다 열고 위험한 것만 막자'는 **무엇이 위험한지 다 알아야 해서
> 불가능**합니다. 반대로 '다 막고 필요한 것만 열자'는 내가 아는 것만 열면 되니까
> **실수해도 안전한 쪽으로 실패**합니다. 이걸 default deny 정책이라고 합니다.
>
> 허용 규칙에 주석을 달아둔 것도 의도적입니다. 몇 달 뒤에 보면
> **왜 이 포트를 열었는지 아무도 기억 못 합니다.** 그러면 지우지도 못하고 그냥 남습니다."

### ★ 꼬리 질문 대비: "컨테이너 재시작하면 왜 꺼져 있나요?"

> "**규칙 파일은 남지만 집행이 사라지기 때문입니다.**
> `/etc/ufw/ufw.conf`의 `ENABLED=yes`와 `user.rules`의 허용 규칙은 파일이라 그대로 있습니다.
> 그런데 그 규칙을 **실제로 집행하는 커널 쪽 iptables 설정**은 컨테이너와 함께 사라집니다.
>
> 보통 서버는 부팅할 때 `systemd`가 ufw를 다시 올려줍니다. **컨테이너엔 systemd가 없습니다.**
> 그래서 `ufw --force enable`을 한 번 더 실행해야 합니다. 파일에 적힌 규칙 그대로 복구됩니다."

**구현 위치** — `setup/04_firewall.sh`

## 1-⑤ 디렉토리 구조·권한 + ACL (권한 분리 실증)

**명령**
```bash
ls -ld ~agent-admin/agent-app/{upload_files,api_keys,bin} /var/log/agent-app
getfacl -p ~agent-admin/agent-app/api_keys
su - agent-test -c 'cat ~agent-admin/agent-app/api_keys/t_secret.key'
```
**나올 결과**
```
drwxrws---+ agent-admin agent-common  upload_files    (2770)
drwxrws---+ agent-admin agent-core    api_keys        (2770)
drwxr-s---+ agent-dev   agent-core    bin             (2750)
...
cat: Permission denied          ← 기대한 결과입니다
```

**읽을 말**

> "**공유 영역과 보안 영역을 나눴고, 나뉘었다는 것을 실제로 거부시켜서 보여드립니다.**
>
> 권한 숫자를 읽어보면 `2770`입니다. 뒤 세 자리 `770`은 소유자 `rwx`, 그룹 `rwx`,
> **그 외는 아무것도 못 함**입니다.
>
> **앞자리 `2`가 `setgid`인데, 이게 실무에서 제일 자주 사고 나는 부분입니다.**
> 이 디렉토리 안에 새로 만들어지는 파일이, 만든 사람의 기본 그룹이 아니라
> **디렉토리의 그룹을 물려받게** 합니다. 이게 없으면 agent-dev가 만든 파일이
> `agent-dev` 그룹이 되어서 **agent-admin이 못 읽는 사고**가 납니다.
>
> ACL을 추가로 쓴 이유는, 전통적인 유닉스 권한은 **'소유자 / 그룹 하나 / 나머지'
> 세 칸뿐**이라서 '이 그룹도 쓰게 해줘'처럼 **대상이 둘 이상이면 표현할 방법이 없기**
> 때문입니다. `setfacl -dm`의 `-d`는 default — **앞으로 만들어질 파일에도 자동 적용**됩니다.
>
> 마지막 줄이 증거입니다. **agent-test로 키 파일을 읽으면 Permission denied가 납니다.**
> 설계가 말로만 있는 게 아니라 실제로 집행되고 있다는 뜻입니다."

**구현 위치** — `setup/02_directories.sh`

## 1-⑥ monitor.sh 프로세스·포트 점검 + **비정상 시 exit 1**

이 항목은 **일부러 고장 내서 보여주는 게 가장 강합니다.**

**명령**
```bash
docker exec agent-ops bash -lc \
  'pkill -f "[a]gent_app\.py"; su - agent-admin -c "$AGENT_HOME/bin/monitor.sh"; echo "exit=$?"'
```
**나올 결과**
```
Checking process 'agent_app.py'... [FAIL]
[FAIL] Process 'agent_app.py' is not running.
exit=1
```
> ⚠️ **끝나면 `./run.sh app`으로 앱을 다시 띄우세요.** 뒤 항목이 전부 이것에 의존합니다.

**읽을 말**

> "앱을 **일부러 죽여서** 보여드리겠습니다. 프로세스가 없으면 `[FAIL]`을 찍고
> **종료 코드 1로 끝납니다.**
>
> 종료 코드를 나눈 게 중요합니다. **0은 정상(경고 포함), 1은 장애, 2는 환경 문제**입니다.
>
> 왜 나눴냐면 — **cron은 스크립트가 0이 아닌 값을 돌려주면 그걸 알림으로 올립니다.**
> 만약 CPU가 21%라고 exit 1을 내면 **매분 알림이 쏟아집니다.** 그러면 사람들이
> 알림을 끄거나 무시하게 되고, **진짜로 프로세스가 죽은 날 아무도 안 봅니다.**
> 이걸 alert fatigue, 알림 피로라고 합니다.
>
> 그래서 **'지금 사용자가 서비스를 못 쓰는 것'만 exit 1**로 했습니다.
> 방화벽이 꺼진 건 고쳐야 할 설정이지만 **당장 서비스는 됩니다.** 그건 경고만 하고 exit 0입니다."

### ★ 꼬리 질문 대비: "왜 `set -e`를 안 쓰셨나요?"

> "**이 스크립트의 일이 '실패를 감지해서 보고하는 것'이기 때문입니다.**
> `set -e`는 명령 하나가 실패하면 즉시 죽습니다. 그러면 프로세스가 죽은 걸 발견한 순간
> **로그를 남기지 못한 채 끝납니다.** 정작 기록해야 할 순간에 기록을 못 하는 거죠.
> 그래서 실패를 직접 확인하고 처리하도록 `set -uo pipefail`만 썼습니다."

### ★ 꼬리 질문 대비: "`pgrep -f`의 함정은 없나요?" (실제로 겪었습니다)

> "있습니다. **명령줄 전체를 보기 때문에 엉뚱한 걸 잡습니다.**
> 다음 미션 B4-2에서 실제로 당했는데, 앱을 띄운 래퍼 셸까지 잡혀서
> **앱이 죽은 뒤에도 '살아 있다'고 거짓 보고**했습니다.
> `/proc/<pid>/comm`을 읽어 셸 종류를 걸러내서 해결했습니다."

**구현 위치** — `bin/monitor.sh`의 `check_process()`, `check_port()`

## 1-⑦ monitor.log **지정 포맷** 누적

**명령**
```bash
tail -5 /var/log/agent-app/monitor.log
```
**나올 결과**
```
[2026-11-23 18:01:03] PID:1234 CPU:12.3% MEM:45.6% DISK_USED:23%
```

**읽을 말 ★ 이 항목이 평가표에서 가장 깊은 질문이 나오는 곳입니다**

> "포맷을 고정한 이유는 **나중에 기계가 읽을 것**이기 때문입니다. 세 가지를 노렸습니다.
>
> ① **라벨 접두사** — `CPU:`처럼 라벨을 붙여두면 awk로 한 줄에서 뽑아낼 수 있고,
> **순서가 바뀌어도 라벨로 찾으면 됩니다.** 실제로 `report.sh`가 이 포맷을 파싱해서
> 평균·최대·최소를 냅니다. **포맷이 흔들리면 분석 스크립트가 전부 깨집니다.**
>
> ② **타임스탬프를 맨 앞에, 사전순 = 시간순 형식으로** — `YYYY-MM-DD HH:MM:SS`는
> **문자열 비교가 곧 시간 비교**입니다. 그래서 구간을 걸러낼 때 날짜 파싱 없이
> 단순 비교로 됩니다. `sort`도 그냥 먹힙니다.
>
> ③ **한 줄에 한 시점** — 여러 줄에 걸치면 `tail`과 `grep`이 무용지물이 됩니다.
> 유닉스 도구는 전부 '한 줄 = 한 레코드'를 전제로 만들어져 있습니다."

### ★ 꼬리 질문 대비: "`>`와 `>>`의 차이를 아세요?"

> "`>`는 **덮어쓰기**고 `>>`는 **이어붙이기**입니다. 로그에 `>`를 쓰면
> **매번 이전 기록이 사라집니다.**
>
> 제 cron 설정이 `monitor.sh >> cron.out 2>&1`입니다. 여기서 `>`를 썼다면
> **매분 파일이 초기화되어 마지막 1분치만** 남습니다. 그러면 장애 추적이 불가능합니다.
> 새벽 3시에 터졌는데 아침에 보면 아침 기록밖에 없으니까요.
>
> 관제의 가치는 **'시간에 따른 변화'**에 있습니다. 메모리가 올라가는 기울기,
> CPU가 튄 시점 — 전부 **누적된 기록이 있어야** 보입니다.
>
> 그리고 `2>&1`은 **에러 출력도 같은 곳으로 보내라**는 뜻입니다. 리눅스는 출력 통로가
> 둘인데 `1`이 표준 출력, `2`가 표준 에러입니다. `>>`만 쓰면 1번만 파일로 가고
> **에러는 그냥 사라집니다.** 정작 알아야 할 건 에러인데요.
>
> **순서도 중요합니다.** `2>&1 >> file`로 쓰면 안 됩니다. 그때는 2번이
> **아직 터미널을 가리키는** 1번을 복사해서, 에러가 파일로 안 갑니다.
> 반드시 `>> file 2>&1` 순서여야 합니다."

# 🟦 항목 2 — 구현 방식과 선택 이유

## 2-1. 프로세스 식별과 포트 확인에 쓴 명령, 그리고 선택 이유

**프로세스 — `pgrep -f`**

> "`pgrep`을 쓴 이유는 `ps | grep`보다 **안전하기 때문**입니다.
> `ps aux | grep agent_app`은 **grep 자기 자신까지 결과에 잡힙니다.**
> 그래서 `grep -v grep`을 또 붙여야 합니다. `pgrep`은 그 문제가 없습니다.
>
> **`-f` 옵션이 중요합니다.** 기본은 **실행 파일 이름만** 봅니다.
> 그런데 `python3 agent_app.py`로 띄우면 프로세스 이름이 `python3`라서
> **`-f` 없이는 못 찾습니다.** `-f`는 **명령줄 전체**에서 찾습니다."

**포트 — `ss -tuln`, `netstat` 폴백**

> "`ss`를 먼저 씁니다. `netstat`은 **deprecated**되어 요즘 배포판엔 기본으로 없을 수 있고,
> `ss`가 더 빠릅니다. **커널의 소켓 정보를 직접 읽거든요.**
> 다만 오래된 서버엔 `ss`가 없을 수 있어서 **`netstat`으로 떨어지게** 해뒀습니다.
>
> 옵션은 `-t`(TCP) `-u`(UDP) `-l`(LISTEN 중) `-n`(이름 해석 안 함)입니다.
> **`-n`이 없으면 DNS 조회를 시도해서 느려집니다.** cron에서 매분 도는 스크립트엔
> 치명적일 수 있습니다."

## 2-2. CPU/MEM/DISK 추출·파싱 방법

| 항목 | 출처 | 파싱 | 핵심 |
|---|---|---|---|
| **CPU** | `/proc/stat` | awk로 1초 간격 **두 번 읽어 차이** | 누적값이라 한 번으론 '지금'을 모름 |
| **MEM** | `/proc/meminfo` | `MemTotal`, **`MemAvailable`** | `MemFree`는 캐시 때문에 늘 작게 나옴 |
| **DISK** | `df -P /` | `awk NR==2 {$5}` | `-P`로 **한 줄 고정** 출력 보장 |

> "**CPU가 제일 까다로웠습니다.** `/proc/stat` 첫 줄은 **부팅 이후 누적 시간**이라
> 한 번만 읽으면 '지금 사용률'을 알 수 없습니다. **1초 간격으로 두 번 읽어 차이**를
> 구해야 그 1초 동안의 사용률이 나옵니다.
> 계산식은 `(전체 증가분 − idle 증가분) ÷ 전체 증가분 × 100`입니다.
>
> 메모리는 **`MemFree`가 아니라 `MemAvailable`을 썼습니다.** 리눅스는 남는 메모리를
> **디스크 캐시로 써 둡니다.** 그래서 `MemFree`는 늘 작게 나오고 '메모리 부족'처럼 보입니다.
> `MemAvailable`은 '필요하면 캐시를 비워서 줄 수 있는 양'까지 계산한 값이라 실제 여유에 가깝습니다.
>
> `df -P`의 `-P`는 **POSIX 출력 형식**입니다. 장치 이름이 길면 df가 줄을 바꿔버리는데,
> `-P`를 주면 한 줄로 고정되어 awk로 **안전하게** 자를 수 있습니다."

### ★ 꼬리 질문: "bash로 소수 비교가 되나요?"

> "안 됩니다. bash의 `-gt`는 정수만 비교합니다. `12.3`을 넣으면 에러가 납니다.
> 그래서 `awk`로 판정하는 `over()` 함수를 따로 만들었습니다."

## 2-3. 소유자(agent-dev)와 실행자(agent-admin, cron) 권한 정책

```
-rwxr-x--- 1 agent-dev agent-core  monitor.sh     (750)
```

> "**소유자는 작성자, 그룹은 실행 권한의 통로**입니다.
>
> | 자리 | 값 | 누가 | 할 수 있는 것 |
> |---|---|---|---|
> | 소유자 | `agent-dev` | 작성자 | `rwx` — 읽고 고치고 실행 |
> | 그룹 | `agent-core` | admin·dev | `r-x` — **읽고 실행만, 수정 불가** |
> | 그 외 | — | agent-test 등 | `---` — **아무것도 못 함** |
>
> cron 실행자인 **agent-admin이 agent-core 그룹에 속해 있어서** 실행할 수 있습니다.
> 하지만 **고칠 수는 없습니다.** 운영자가 스크립트를 임의로 바꾸지 못하게 한 겁니다.
> agent-test는 그룹에 없으니 **실행 자체가 거부**됩니다."

## 2-4. 용량 기반 로그 관리(10MB/10개)를 어떤 방식으로 구현했나?

### ④ 읽을 말

> "**logrotate를 쓰지 않고 `monitor.sh` 안에 직접 구현**했습니다.
>
> logrotate는 리눅스가 기본으로 제공하는 로그 정리 도구인데, **자기 cron으로
> 보통 하루에 한 번** 돕니다. 제 `monitor.sh`는 **매분** 돌고, 돌 때마다 로그 크기를
> 직접 확인합니다. 그래서 **10MB를 넘는 순간 바로 정리됩니다.**
> logrotate에 맡기면 하루 한 번이라 **그 사이에 로그가 폭증하면 못 막습니다.**
> 패키지 의존성이 없어진다는 장점도 있습니다.
>
> 방식은 **번호를 밀어내는 회전**입니다. `monitor.log`가 10MB를 넘으면
> `monitor.log.1`로 옮기고, 기존 `.1`은 `.2`로, 그렇게 `.10`까지 밀고
> **가장 오래된 `.10`은 버립니다.** 그래서 디스크 사용량이 **최대 110MB로 고정**됩니다.
>
> **반드시 뒤에서부터 밀어야 합니다.** `.9` 삭제 → `.8`을 `.9`로 → … →
> `.1`을 `.2`로 → 마지막에 `monitor.log`를 `.1`로.
> **앞에서부터 밀면 `.1`이 `.2`를 덮어쓰면서 기록이 전부 사라집니다.**"

### ★ 꼬리 질문 대비: "왜 10MB인가요?"

> "특별한 근거가 있는 숫자는 아니고, **한 줄이 약 100바이트이니 10MB면 10만 줄**,
> 매분 1줄씩 쌓이면 **약 70일치**입니다. 10개를 보관하니 **2년 가까이 남습니다.**
> 과제 요구가 10MB/10개여서 그대로 맞췄고, 바꾸려면 `monitor.sh`의 상수 두 개만
> 고치면 됩니다."

## 3-3. "경고는 출력하되 종료하지 않는 항목"을 분리한 운영상 이유 ★

| 구분 | 예 | 처리 | 왜 |
|---|---|---|---|
| **장애** | 프로세스 죽음, 포트 안 열림 | **exit 1** | **지금 사용자가 서비스를 못 씁니다** |
| **경고** | 방화벽 꺼짐, CPU 임계치 초과 | 출력만, **exit 0** | 당장 서비스는 됩니다. 사람이 판단할 일 |

### ④ 읽을 말

> "**cron은 스크립트가 0이 아닌 값을 돌려주면 그걸 알림으로 올립니다.**
> 그래서 어떤 상황에 0이 아닌 값을 낼지가 **그대로 알림 정책이 됩니다.**
>
> 만약 CPU가 21%라고 exit 1을 내면 **매분 알림이 쏟아집니다.** 그러면 사람들이
> 알림을 끄거나 무시하게 되고, **진짜로 프로세스가 죽은 날 아무도 안 봅니다.**
> 이걸 **alert fatigue, 알림 피로**라고 합니다.
>
> 그래서 기준을 하나로 정했습니다 — **'지금 사용자가 서비스를 못 쓰는 것'만 exit 1**입니다.
> 프로세스가 죽었거나 포트가 안 열린 건 **지금 당장 서비스가 안 되는 것**이라 exit 1입니다.
> 방화벽이 꺼진 건 고쳐야 할 설정이지만 **당장 서비스는 됩니다.** 그건 경고만 하고 exit 0입니다.
>
> 정리하면 **'고쳐야 하는 것'과 '지금 터진 것'을 구분한 것**입니다.
> 둘을 같은 코드로 만들면 **알림이 의미를 잃습니다.**"

### ★ 꼬리 질문 대비: "그럼 방화벽이 꺼진 건 어떻게 알게 되나요?"

> "로그에 남습니다. `monitor.log`에 매분 기록되니까 `report.sh`로 요약하면
> **'며칠째 방화벽 경고가 떠 있다'가 보입니다.**
> **즉시 알림이 필요한 것과 추이로 봐야 하는 것을 다른 통로로 나눈 것**입니다."

## 3-4. ★ 리다이렉션 `>`와 `>>`의 차이, 로그 누적에 `>>`가 필요한 이유

### ④ 읽을 말

> "`>`는 **덮어쓰기**고 `>>`는 **이어붙이기**입니다. 로그에 `>`를 쓰면
> **매번 이전 기록이 사라집니다.**
>
> 제 cron 설정이 `monitor.sh >> cron.out 2>&1`입니다. 여기서 `>`를 썼다면
> **매분 파일이 초기화되어 마지막 1분치만** 남습니다. 그러면 장애 추적이 불가능합니다.
> 새벽 3시에 터졌는데 아침에 보면 **아침 기록밖에 없으니까요.**
>
> 관제의 가치는 **'시간에 따른 변화'**에 있습니다. 메모리가 올라가는 기울기,
> CPU가 튄 시점 — 전부 **누적된 기록이 있어야** 보입니다.
> 한 시점의 값만 있으면 '지금 80%'인 건 알지만 **'올라가는 중인지 내려가는 중인지'를
> 모릅니다.** 그 둘은 완전히 다른 상황입니다."

### ★ 함께 말하면 좋은 것: `2>&1`은 무엇인가

> "`2>&1`은 **에러 출력도 같은 곳으로 보내라**는 뜻입니다.
> 리눅스는 출력 통로가 둘인데 **`1`이 표준 출력, `2`가 표준 에러**입니다.
> `>>`만 쓰면 1번만 파일로 가고 **에러는 그냥 사라집니다.**
> 정작 알아야 할 건 에러인데요.
>
> **순서도 중요합니다.** `2>&1 >> file`로 쓰면 안 됩니다. 그때는 2번이
> **아직 터미널을 가리키는** 1번을 복사해서, 에러가 파일로 안 갑니다.
> 반드시 **`>> file 2>&1` 순서**여야 합니다. 이건 '복사'라서, 복사하는 시점에
> 1번이 어디를 보고 있었는지가 결과를 바꿉니다."

# 🟦 항목 4 — 응용 (가장 어려운 항목)

## 4-1. 모니터링 대상이 Nginx로 바뀐다면 바꿔야 할 핵심 포인트

> "**네 가지**입니다. 그리고 **스크립트 구조는 안 바꿔도 됩니다** — 전부 환경변수로 빼뒀거든요."

| 포인트 | 지금 | Nginx라면 | 주의할 점 |
|---|---|---|---|
| **프로세스** | `agent_app.py` | `nginx` | ★ **마스터 1 + 워커 N** 구조. 하나만 세면 안 되고 **마스터 생존**을 봐야 함 |
| **포트** | 15034 | **80, 443** | 두 개를 **모두** 확인. **443만 죽는 경우가 흔함** |
| **로그** | `/var/log/agent-app/` | `access.log`, `error.log` | **에러 로그를 따로** 봐야 함 |
| **임계값** | CPU 20 / MEM 10 | **훨씬 높게** | 웹 서버는 평상시에도 더 씀. 20%로 두면 **거짓 경고 폭탄** |

```bash
export AGENT_PROC=nginx
export AGENT_PORT=80
export AGENT_LOG_DIR=/var/log/nginx
```

> "**가장 중요한 건 임계값입니다.** 대상이 바뀌면 '정상'의 기준도 바뀝니다.
> 지금 값을 그대로 쓰면 Nginx는 **평상시에도 계속 경고**를 냅니다. 바로 alert fatigue입니다.
>
> 그리고 웹 서버는 **살아 있는지보다 응답하는지**가 중요합니다.
> `curl -f http://localhost/health` 같은 **실제 요청 검사**를 추가해야 합니다.
> **프로세스가 떠 있어도 응답을 못 할 수 있으니까요** — 바로 다음 질문입니다."

## 4-2. ★ "프로세스는 살아있는데 포트가 안 열리는" 상황 — 원인과 확인 순서

> **평가표에서 가장 실무적인 질문입니다. 순서대로 답하세요.**

**원인 후보 5가지**

| # | 원인 | 왜 생기나 |
|---|---|---|
| 1 | **바인딩 실패 후에도 프로세스가 살아 있음** | 포트가 이미 쓰이는데 에러 처리를 안 해 그냥 계속 돎 |
| 2 | **127.0.0.1에만 바인딩** | `0.0.0.0`이 아니라 루프백에만 열려 외부에서 안 보임 |
| 3 | **초기화 중 멈춤 / 교착상태** | 프로세스는 살아 있지만 `listen()`까지 도달 못 함 |
| 4 | **방화벽이 막음** | 앱은 열었는데 UFW 규칙이 없음 |
| 5 | **다른 포트에 열림** | 환경변수를 잘못 읽어 엉뚱한 포트 |

**확인 순서 — 안쪽에서 바깥쪽으로**

```bash
# ① 정말 안 열렸나? (앱 기준)
ss -tulnp | grep <PID>
   → 아예 없다        → 앱이 bind 를 못 했다 (원인 1·3)
   → 127.0.0.1:15034  → 바인딩 주소 문제 (원인 2)
   → 다른 포트         → 설정 문제 (원인 5)

# ② 앱이 어디서 멈췄나?
tail -20 <앱 로그>
   → "Port ... unavailable" → 원인 1
   → 중간에 끊김             → 원인 3 (교착 의심)

# ③ 멈춘 거라면 — 스레드 상태
ps -L -p <PID> -o tid,stat,wchan
   → 전부 S + futex_wait → 교착상태

# ④ 앱은 열었는데 밖에서 안 될 때
curl localhost:15034        # 안에서 되면 앱은 정상
ufw status                  # 규칙 확인 (원인 4)
```

> "**순서가 중요합니다. 방화벽부터 보면 안 됩니다.**
> **앱이 실제로 열었는지** 먼저 확인해야 범위가 좁혀집니다.
> `ss` 결과가 비어 있으면 **방화벽은 볼 필요도 없습니다.**
>
> ③번이 교착상태인데 다음 미션 B4-2에서 실제로 다뤘습니다.
> `wchan`이 `futex_wait`면 락을 기다리는 중이라는 **커널 레벨 증거**입니다."

## 4-3. 로그 급증으로 디스크가 찰 위험 — 단기/중기 대응

> "나눠서 답하겠습니다. **지금 당장 서비스를 살리는 것**과
> **다시 안 일어나게 하는 것**은 다른 일입니다."

**먼저 — 왜 급한가**

> "디스크가 100%가 되면 **로그를 못 쓰는 정도가 아니라 서비스가 멈춥니다.**
> 임시 파일도 못 만들고 DB 쓰기도 실패합니다.
> **장애를 기록하려던 것이 장애의 원인이 됩니다.**"

**단기 (수 분 안에)**

| 순서 | 조치 | 주의 |
|---|---|---|
| 1 | `df -h`, `du -sh /var/log/*`로 **범인 찾기** | 추측하지 말고 확인 |
| 2 | 오래된 로그 **압축**(`gzip`) | 텍스트는 1/10 이하로 줄어듦 |
| 3 | 아주 오래된 것 정리 | ★ `rm` 말고 **truncate** (아래) |
| 4 | 로그 레벨 **DEBUG → INFO** | 증상 완화 |

> ⚠️ **`rm`의 함정 — 이걸 말하면 아는 사람입니다.**
>
> "**앱이 열고 있는 로그 파일을 `rm`하면 디스크가 안 비워집니다.**
> 파일 이름만 사라지고, 프로세스가 **파일 디스크립터를 쥐고 있어서** 용량은 그대로입니다.
> `df`는 꽉 찬 채인데 `du`로는 안 보이는 상황이 됩니다.
> 그래서 `truncate -s 0 <파일>`로 **내용만 비우거나**, 앱을 재시작해 핸들을 놓게 해야 합니다."

**중기 (재발 방지)**

| 순서 | 조치 | 해결하는 것 | 구현 |
|---|---|---|---|
| 1 | **보존 정책 자동화** — 7일 압축 / 30일 삭제 | 사람이 안 해도 정리됨 | ✅ `bin/log_archive.sh` |
| 2 | **용량 기반 회전** 10MB/10개 | 한 파일이 무한정 커지는 것 방지 | ✅ `bin/monitor.sh` |
| 3 | **로그 레벨 정리** | 양 자체를 줄임 | |
| 4 | **디스크 80% 경고** | 꽉 차기 **전에** 알림 | ✅ `bin/monitor.sh` |
| 5 | **로그 분리 파티션** | 로그가 터져도 **시스템은 멀쩡** | |
| 6 | 중앙 로그 수집 | 서버에 쌓지 않음 | |

> "**1·2·4번은 이미 구현해뒀습니다.**
> 5번이 특히 좋은 대비입니다. `/var/log`를 **별도 파티션**으로 두면
> 로그가 가득 차도 **루트 파티션은 멀쩡해서 서버가 죽지 않습니다.**
> 로그만 못 쓰고 서비스는 계속 됩니다."

# 🟦 마지막 — "경험 정도 (재구현 가능 여부)"

평가표 맨 아래에서 평가자가 **"이 사람이 다시 만들 수 있을까"** 를 체크합니다.
**항목 1~5와 따로 매겨집니다** — 항목을 다 맞혀도 여기서 깎일 수 있습니다.

이 미션은 재료가 가장 많습니다. **실제로 막혔다가 해결한 문제가 네 개** 있고,
전부 `docs/수행내역서.md` 7절에 기록돼 있습니다. 앞쪽 항목 1에서 두 개(①②)는 이미
꼬리 질문 대비로 썼지만, **여기서 네 개를 묶어 말하는 게 훨씬 강합니다.**

**① `pkill`이 자기 자신을 죽였다**

> "앱을 죽이려고 `pkill -f agent_app.py`를 썼는데 **스크립트가 먼저 죽었습니다.**
> `-f`는 **명령줄 전체를 보고 찾는데**, `pkill`을 호출한 셸의 명령줄에도
> `agent_app.py`라는 글자가 들어 있었던 겁니다. **자기가 자기를 찾아서 죽였습니다.**
>
> 대괄호 트릭(`[a]gent_app`)으로 해결했습니다. 정규식으로는 `agent_app`과 같은데
> **글자 그대로는 다르니까** 자기 명령줄에는 안 걸립니다."

**② 방화벽이 켜져 있는데 "꺼졌다"고 거짓 경고가 났다**

> "`ufw`는 분명히 활성 상태인데 `monitor.sh`가 '방화벽이 꺼져 있다'고 경고했습니다.
>
> 원인은 **`ufw status`가 root 전용 명령**이라는 것이었습니다. cron은 일반 계정
> (`agent-admin`)으로 도니까, **권한이 없어서 상태를 못 읽고 '꺼짐'으로 판정**한 겁니다.
> **방화벽이 꺼진 게 아니라 확인을 못 한 거였습니다.**
>
> 해결은 두 단계였습니다. ① `sudoers.d`에 **`ufw status`만** 허용하는 최소 권한 규칙을
> 넣고 ② 그래도 안 되는 환경을 대비해 **3단 폴백**(`sudo ufw status` → `ufw status` →
> `/etc/ufw/ufw.conf` 직접 읽기)을 뒀습니다.
>
> 이 일로 배운 건 **'확인 실패'와 '실제 실패'를 구분해야 한다**는 점입니다.
> 거짓 경고가 계속 나면 사람이 **진짜 경고도 무시하기 시작합니다.**"

**③ `report.sh`가 로그를 한 줄도 못 읽었다**

> "로그에 줄이 분명히 있는데 '분석할 데이터가 없습니다'가 나왔습니다.
>
> 원인은 **awk의 종류**였습니다. 날짜를 뽑으려고 `[0-9]{4}` 같은 **구간 수량자**를
> 썼는데, **Ubuntu의 기본 awk는 gawk가 아니라 mawk**이고 mawk 1.3.4는 `{n}` 문법을
> 지원하지 않습니다. 그래서 **아무것도 매치되지 않았습니다.**
>
> 정규식을 버리고 `index()`와 `substr()`로 대괄호 위치를 직접 찾게 바꿨습니다.
> **어느 awk에서도 똑같이 동작합니다.**
>
> 같은 이름의 명령이라도 **어느 구현이 깔려 있느냐에 따라 동작이 다르다**는 걸
> 이때 알았습니다."

**④ 컨테이너가 자꾸 꺼졌다**

> "`docker exec`로 접속했다가 나오면 **컨테이너가 같이 종료됐습니다.**
>
> 컨테이너의 메인 프로세스(PID 1)를 `bash`로 뒀던 게 원인입니다. 그 bash가 EOF를
> 받으면 종료되고, **PID 1이 죽으면 컨테이너도 죽습니다.**
> `CMD ["sleep", "infinity"]`로 바꿔서 해결했습니다 — 아무 입출력에도 영향받지 않습니다."

**덧붙이면 좋은 것 — "알고도 이렇게 했습니다"**

> "`monitor.sh`에 **`set -e`를 일부러 넣지 않았습니다.** 보통은 넣는 게 좋은 습관인데,
> 이 스크립트의 **일이 바로 '실패를 보고하는 것'**입니다. `set -e`를 넣으면
> **첫 실패에서 스크립트가 죽어서 나머지 점검을 못 하고 로그도 안 남깁니다.**
> 그러면 감시 도구가 감시를 못 하게 됩니다."

> "그리고 **제공된 앱을 아직 받지 못해서** 과제 PDF 6~7쪽의 Boot Sequence 5단계와
> 출력 형식을 그대로 구현한 **대역(stand-in)**으로 개발했습니다. 감시 대상 프로세스
> 이름을 `AGENT_PROC` 환경변수로 받기 때문에 **실제 앱을 받으면 한 줄만 바꾸면 되고
> `monitor.sh`는 고칠 필요가 없습니다.** 이건 숨기지 말고 먼저 말하는 게 좋습니다."

> 💡 **"알고도 이렇게 선택했다"를 말할 수 있으면** 재구현 가능한 사람으로 보입니다.
> 특히 ②번은 **'왜 그렇게 보였는가'까지 설명**하는 이야기라서 가장 효과가 좋습니다.
