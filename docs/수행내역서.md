# 미션 B4-1 요구사항 수행 내역서

**미션** 컴퓨터가 알아서 자기 상태를 점검하게 만들기
**분야** AI/SW 기초 · 구분 Linux와 OS · 학습시간 40시간
**수행 환경** Ubuntu 22.04.5 LTS (Docker 컨테이너, hostname `agent-ops`)
**저장소** https://github.com/haeunyn/agent-ops

> 증거 자료는 `./run.sh evidence` 로 언제든 전부 재생성할 수 있습니다.
> 아래 출력은 실제 실행 결과입니다.

## 0. 실행 환경을 컨테이너로 잡은 이유

이 미션은 **SSH 포트 변경, root 로그인 차단, 방화벽 활성화, 시스템 계정 생성**을
요구합니다. 이걸 쓰던 노트북에 그대로 적용하면 되돌리기 어렵고, 설정을 잘못 하면
내 컴퓨터에 접속하지 못하게 될 수도 있습니다.

컨테이너 안에서 하면

- 실제 Ubuntu 와 **똑같이** 동작한다 (진짜 `useradd`, 진짜 `ufw`, 진짜 `cron`)
- 호스트 설정은 **전혀 건드리지 않는다**
- 망가뜨려도 `./run.sh down && ./run.sh up` 한 번이면 처음부터 다시 할 수 있다
- 평가자가 **같은 환경을 그대로 재현**할 수 있다

UFW 가 iptables 규칙을 넣으려면 권한이 필요해서 `cap_add: [NET_ADMIN, SYS_ADMIN]`
을 줬습니다. 이게 없으면 `ufw enable` 이 권한 오류로 실패합니다.

## 1. 기본 보안 및 네트워크 설정

### 1-1. SSH (`setup/03_ssh.sh`)

| 항목 | 설정값 |
|---|---|
| Port | **20022** (기본 22 에서 변경) |
| PermitRootLogin | **no** |

```
# grep -E "^(Port|PermitRootLogin)" /etc/ssh/sshd_config
Port 20022
PermitRootLogin no

# ss -tulnp | grep sshd
tcp LISTEN 0 128 0.0.0.0:20022 0.0.0.0:* users:(("sshd",pid=370,fd=3))
tcp LISTEN 0 128    [::]:20022    [::]:* users:(("sshd",pid=370,fd=4))
```

**왜 포트를 바꾸는가** — 22번은 전 세계가 아는 기본 포트입니다. 서버를 인터넷에
올리면 몇 분 안에 자동 스캐너가 22번을 두드리며 아이디/비밀번호를 무작위로
시도합니다. 포트를 옮기면 그 자동화된 소음이 거의 사라집니다.
다만 이건 **보안의 완성이 아니라 소음 제거**입니다. 포트 스캔으로 찾아낼 수 있으니
키 인증·방화벽과 **함께** 써야 의미가 있습니다.

**왜 root 원격 로그인을 막는가** — 공격자 입장에서 root 는 *아이디를 맞힐 필요가
없는* 계정입니다. 비밀번호만 뚫으면 끝이고 성공하면 즉시 시스템 전체를 잡습니다.
일반 계정으로 로그인 후 `sudo` 를 쓰게 하면 ① 아이디까지 맞혀야 하고
② 누가 무슨 명령을 했는지 로그에 남습니다.

### 1-2. 방화벽 — UFW (`setup/04_firewall.sh`)

```
# ufw status verbose
Status: active
Default: deny (incoming), allow (outgoing), deny (routed)

To                  Action      From
--                  ------      ----
20022/tcp           ALLOW IN    Anywhere    # SSH (changed from 22)
15034/tcp           ALLOW IN    Anywhere    # Agent App
20022/tcp (v6)      ALLOW IN    Anywhere (v6)
15034/tcp (v6)      ALLOW IN    Anywhere (v6)
```

적용한 명령:

```bash
ufw default deny incoming      # 기본은 전부 차단
ufw default allow outgoing
ufw allow 20022/tcp comment 'SSH (changed from 22)'
ufw allow 15034/tcp comment 'Agent App'
ufw --force enable
```

**왜 '기본 차단'부터 시작하는가** — 열린 포트 하나하나가 공격 표면입니다.
"일단 다 열고 위험한 것만 막자"는 무엇이 위험한지 전부 알아야 하므로 불가능합니다.
반대로 "다 막고 필요한 것만 열자"는 **내가 아는 것만 열면 되므로, 실수해도 안전한
쪽으로 실패**합니다. 이것이 `default deny` 정책입니다.

UFW 를 고른 이유는 Ubuntu 기본 도구이고 iptables 를 쉬운 말로 감싼 것이라
규칙이 읽기 쉬워서입니다. firewalld 는 RHEL 계열에서 주로 쓰고, **둘을 섞으면
규칙이 충돌**하므로 하나만 씁니다.

## 2. 계정 / 그룹 / 권한 체계 (`setup/01`, `setup/02`)

### 2-1. 계정과 그룹

```
# id agent-admin
uid=1000(agent-admin) gid=1002(agent-admin) groups=1002(agent-admin),1000(agent-common),1001(agent-core)
# id agent-dev
uid=1001(agent-dev)   gid=1003(agent-dev)   groups=1003(agent-dev),1000(agent-common),1001(agent-core)
# id agent-test
uid=1002(agent-test)  gid=1004(agent-test)  groups=1004(agent-test),1000(agent-common)

# getent group agent-common
agent-common:x:1000:agent-admin,agent-dev,agent-test
# getent group agent-core
agent-core:x:1001:agent-admin,agent-dev
```

| 계정 | 역할 | agent-common | agent-core |
|---|---|:---:|:---:|
| agent-admin | 운영/관리, cron 실행자 | ✅ | ✅ |
| agent-dev | 개발/운영, monitor.sh 작성자 | ✅ | ✅ |
| agent-test | QA/테스트 | ✅ | ❌ |

**왜 역할마다 계정을 나누는가** — 한 계정을 돌려쓰면 "누가 무엇을 했는지" 추적이
안 되고, 하나가 뚫리면 전부 뚫립니다. 역할별로 나누면 **피해 범위가 그 역할로
제한**됩니다 (최소 권한 원칙).

**왜 그룹이 두 개인가** — `agent-common` 은 셋 다 쓰는 공유 영역용,
`agent-core` 는 admin·dev 만 쓰는 보안 영역용입니다. test 는 core 에 없으므로
API 키를 들여다볼 수 없습니다.

### 2-2. 디렉토리 구조와 권한

```
drwxr-s---  agent-admin agent-core    /home/agent-admin/agent-app
drwxrws---+ agent-admin agent-common  /home/agent-admin/agent-app/upload_files
drwxrws---+ agent-admin agent-core    /home/agent-admin/agent-app/api_keys
drwxr-s---  agent-dev   agent-core    /home/agent-admin/agent-app/bin
drwxrws---+ agent-admin agent-core    /var/log/agent-app
```

**`2770` 의 앞자리 `2` 는 setgid** 입니다. 이 디렉토리 안에 새로 만들어지는 파일이
만든 사람의 기본 그룹이 아니라 **디렉토리의 그룹**을 물려받게 합니다.
이게 없으면 agent-dev 가 만든 파일이 `agent-dev` 그룹이 되어 agent-admin 이
못 읽는 사고가 납니다.

**ACL 이 추가로 필요한 이유** — 전통적인 권한은 `소유자 / 그룹 하나 / 나머지`
세 칸뿐입니다. 대상이 둘 이상이면 표현할 방법이 없습니다. ACL 은 그 제약을 풉니다.
`-d`(default) ACL 은 앞으로 만들어질 파일에도 자동 적용됩니다.

```
# getfacl api_keys
user::rwx
user:agent-test:---        ← test 는 명시적으로 차단
group::rwx
group:agent-core:rwx
other::---
default:group:agent-core:rwx
```

**권한 분리 실증** — 말이 아니라 실제로 막히는지 확인했습니다.

```
# su - agent-test -c "cat .../api_keys/t_secret.key"
cat: /home/agent-admin/agent-app/api_keys/t_secret.key: Permission denied
```

### 2-3. monitor.sh 배치 권한

```
-rwxr-x--- 1 agent-dev agent-core monitor.sh       (750)
-rwxr-x--- 1 agent-dev agent-core report.sh        (750)
-rwxr-x--- 1 agent-dev agent-core log_archive.sh   (750)
```

소유자 `agent-dev`(작성자), 그룹 `agent-core`, 권한 `750`.
cron 실행자인 agent-admin 은 agent-core 에 속하므로 실행할 수 있고,
agent-test 는 그룹에 없어 **실행 자체가 거부**됩니다.

## 3. 애플리케이션 실행 환경 (`setup/05_env.sh`)

```
AGENT_HOME       = /home/agent-admin/agent-app
AGENT_PORT       = 15034
AGENT_UPLOAD_DIR = $AGENT_HOME/upload_files
AGENT_KEY_PATH   = $AGENT_HOME/api_keys/t_secret.key
AGENT_LOG_DIR    = /var/log/agent-app
AGENT_PROC       = agent_app.py
```

`/etc/profile.d/agent-app.sh` 에 등록했습니다.
키 파일 `t_secret.key` 내용은 `agent_api_key_test` 한 줄, 권한 `640`.

**왜 환경 변수로 빼는가**
1. "내 컴퓨터에선 되는데요"를 막습니다. 환경이 달라도 코드는 그대로 둡니다.
2. **cron 에서 특히 중요합니다.** cron 은 로그인 셸이 아니라 `.bashrc` 를 읽지
   않고 PATH 조차 최소한만 줍니다. 그래서 스크립트가 **자기 환경을 스스로
   불러오도록** 만들어야 합니다 (`monitor.sh` 맨 위에서 이 파일을 `source` 하는 이유).
3. 키 경로를 소스에 박으면 저장소에 올라가 유출됩니다.

### 4-4. 종료 코드 설계

| 코드 | 의미 |
|---|---|
| 0 | 정상 (경고가 있어도 0) |
| 1 | Health Check 실패 — 프로세스/포트 이상 |
| 2 | 환경 문제 — 로그 디렉토리 접근 불가 |

**경고와 장애를 나눈 이유** — cron 은 0이 아닌 종료 코드를 알림으로 올립니다.
둘을 같은 코드로 만들면 알림이 쏟아져 **진짜 장애를 놓칩니다.**

### 4-5. 자원 수집 방법

| 항목 | 출처 | 핵심 |
|---|---|---|
| CPU | `/proc/stat` | 부팅 이후 **누적값**이라 1초 간격 두 번 읽어 **차이**로 계산 |
| MEM | `/proc/meminfo` | `MemFree` 가 아니라 **`MemAvailable`** 사용 |
| DISK | `df -P /` | `-P` 로 한 줄 고정 출력 보장 |

**왜 MemAvailable 인가** — 리눅스는 남는 메모리를 디스크 캐시로 써둡니다.
그래서 `MemFree` 는 늘 작게 나와 "메모리 부족"처럼 보입니다. `MemAvailable` 은
*필요하면 캐시를 비워서 줄 수 있는 양*까지 계산한 값이라 실제 여유에 가깝습니다.

```

```

검증 방법: `touch -d "N days ago"` 로 파일 시각을 인위적으로 옮겨 테스트했습니다.

| 파일 | 나이 | 기대 | 결과 |
|---|---|---|---|
| `old8.log` | 8일 | 압축·이동 | ✅ |
| `monitor.log.1` | 10일 | 압축·이동 | ✅ |
| `old3.log` | 3일 | **그대로 둠** | ✅ |
| `ancient.log.gz` | 40일 | 삭제 | ✅ |
| `monitor.log` | 현재 | **그대로 둠** | ✅ |

**왜 보존 정책이 필요한가** — 로그는 지우지 않으면 반드시 디스크를 채웁니다.
디스크가 100% 가 되면 로그를 못 쓰는 정도가 아니라 **서비스 자체가 멈춥니다.**
장애를 기록하려던 것이 장애의 원인이 되는 셈입니다.
그렇다고 바로 지울 수도 없습니다. 장애 분석은 보통 며칠 뒤에 합니다.
그래서 *최근은 그대로 / 조금 지난 건 압축 / 아주 오래된 건 삭제* 3단계로 나눕니다.

## 7. 수행 중 겪은 문제와 해결

### 7-1. `pkill` 이 자기 자신을 죽였다

앱을 재시작하는 스크립트가 아무 출력 없이 종료 코드 **143**(= SIGTERM)으로 끝났습니다.

**원인** — `pkill -f agent_app.py` 의 `-f` 는 *명령줄 전체*에서 찾습니다.
그런데 이 pkill 을 실행한 셸의 명령줄에도 `agent_app.py` 라는 문자열이
들어 있어서, **pkill 이 자기를 호출한 셸을 죽인 것**입니다.

**해결** — 대괄호 트릭.

```bash
pkill -f '[a]gent_app\.py'
```

정규식으로는 `agent_app.py` 에 매치되지만, 문자열 자체는 `[a]gent_app.py` 라서
자기 명령줄과는 겹치지 않습니다.

### 7-2. 방화벽이 켜져 있는데 "꺼졌다"고 거짓 경고

`monitor.sh` 가 `[WARNING] Firewall (ufw) is not active` 를 냈는데,
root 로 확인하니 `Status: active` 였습니다.

**원인** — `ufw status` 는 **root 전용**입니다. cron 은 agent-admin 으로 돌기
때문에 `ERROR: You need to be root` 가 나왔고, 스크립트는 그걸 "active 아님"으로
해석했습니다.

**왜 이게 심각한가** — 모니터링에서 **거짓 경고는 단순한 흠이 아닙니다.**
경고에 무뎌지게 만들어서, 진짜 장애가 왔을 때 아무도 안 보게 됩니다(alert fatigue).

**해결** — 두 겹으로 막았습니다.

1. `/etc/sudoers.d/agent-monitor` 에 **`ufw status` 딱 하나만** 비밀번호 없이
   허용 (`NOPASSWD: ALL` 로 열면 사실상 root 를 준 것과 같으므로 최소 권한으로)
2. `monitor.sh` 는 ① root 면 그대로 ② 아니면 `sudo -n` ③ 그것도 안 되면
   `/etc/ufw/ufw.conf` 를 직접 읽는 **3단 폴백**

`sudo -n` 의 `-n` 은 "비밀번호를 물어야 하면 그냥 실패하라"는 뜻입니다.
cron 은 입력을 받을 수 없으므로 반드시 필요합니다.

### 7-3. `report.sh` 가 로그를 한 줄도 못 읽었다

로그에 줄이 분명히 있는데 "분석할 데이터가 없습니다" 가 나왔습니다.

**원인** — awk 정규식에서 `[0-9]{4}` 같은 **구간 수량자**를 썼는데,
Ubuntu 의 기본 awk 는 gawk 가 아니라 **mawk** 입니다. `mawk 1.3.4` 는
`{n}` 문법을 지원하지 않아 아무것도 매치되지 않았습니다.

```
$ echo "[2026-10-31 06:34:14] x" | awk '{ if (match($0, /\[[0-9]{4}-.../)) ... }'
매치 실패
```

**해결** — 정규식 대신 `index()` / `substr()` 로 대괄호 위치를 직접 찾도록
바꿨습니다. 어느 awk 에서도 똑같이 동작합니다.

### 7-4. 컨테이너가 자꾸 꺼졌다

`docker exec` 이 끊길 때 컨테이너가 함께 종료됐습니다.

**원인** — 컨테이너의 메인 프로세스(PID 1)를 `bash` 로 뒀는데, 그 bash 가
EOF 를 받으면 종료되고 **PID 1 이 죽으면 컨테이너도 죽습니다.**

**해결** — `CMD ["sleep", "infinity"]`. 아무 입출력에도 영향받지 않습니다.
